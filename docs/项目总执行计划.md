# 多模态大模型 + Agent + 手机 App + 微信小程序：Linux 单服务器端到端执行方案

> **最终目标：在 Linux GPU 服务器上完整跑通**  ** ****Qwen3-VL → 多模态数据 → LoRA SFT → GRPO → vLLM → LangGraph/LangChain Agent → FastAPI → 手机 App → 微信小程序**。
>
> **Windows 不承载模型、Agent、后端或项目源码；它只作为 SSH/VS Code Remote-SSH、浏览器、Android/iOS 测试设备辅助工具和微信开发者工具使用。**
>
> **所有项目源码、模型、训练脚本、Agent、后端、App 源码、小程序源码均存放在 Linux 服务器的一个 Git 仓库中。**

# 3. 为什么 App 和微信小程序不直接连接 vLLM

**不要：**

```
App
  ↓
vLLM :8000
```

**也不要：**

```
小程序
  ↓
vLLM :8000
```

**正确结构：**

```
App / 小程序
      │
      ▼
     Nginx
      │
      ▼
    FastAPI
      │
      ▼
     Agent
      │
      ▼
     vLLM
```

**FastAPI 负责：**

```
登录
JWT
用户 ID
会话管理
消息历史
图片上传
视频上传
限流
错误处理
审计日志
Agent 调度
Tool Calling
RAG
Memory
```

**vLLM 只负责：**

```
高性能模型推理
```

**因此：**

```
vLLM:
127.0.0.1:8000

FastAPI:
127.0.0.1:9000

Nginx:
0.0.0.0:443
```

**公网只开放：**

```
443
```

# 4. 为什么统一使用 WebSocket 做流式聊天

**AI Chat 最重要的体验之一：**

```
用户发送消息
↓
模型边生成
↓
客户端边显示
```

**手机 App 可以用：**

```
WebSocket
```

**微信小程序也可以用：**

```
wx.connectSocket / Taro.connectSocket
```

**所以本项目统一：**

```
HTTPS
用于：
登录
历史记录
文件上传
普通 CRUD

WSS / WebSocket
用于：
LLM 流式聊天
Agent 事件
Token 增量返回
Tool 状态事件
```

**最终：**

```
wss://api.example.com/ws/chat
```

**两个客户端都使用同一套消息协议。**

# 5. 为什么不把 SSE 作为主方案

**Web App 中 SSE 非常方便。**

**但本项目现在明确有：**

```
React Native
+
微信小程序
```

**为了减少两套流式实现：**

```
统一 WebSocket
```

**更合适。**

**微信小程序也可以使用：**

```
wx.request({
    enableChunked: true
})
```

**配合 **`onChunkReceived()` 做分块流式。

**这个方案可以作为备用。**

**但是 V1 主方案统一：**

```
WebSocket
```

# 7. 为什么 App 和小程序仍然需要两个项目

**虽然它们都使用：**

```
React
+
TypeScript
```

**但是运行环境不同。**

**App：**

```
React Native
↓
Android / iOS 原生控件
```

**小程序：**

```
Taro
↓
编译成微信小程序组件/API
```

**所以不能指望：**

```
100% UI 代码共享
```

**真正应该共享的是：**

```
API 类型
WebSocket 消息协议
DTO
业务模型
部分纯 TypeScript 工具函数
```

**例如：**

```
packages/api-contract/
packages/chat-protocol/
```

**而：**

```
ChatBubble
Image Picker
Navigation
Storage
Login UI
```

**分别实现。**

**这是比强行“一套 UI 跑所有端”更稳定的方案。**

# 16. Reward

**第一版：**

```
Accuracy Reward
+
Format Reward
```

**要求：**

```
<answer>3</answer>
```

**Accuracy：**

```
def accuracy_reward(prediction: str, solution: str) -> float:
    return 1.0 if prediction.strip() == solution.strip() else 0.0
```

**Format：**

```
import re


def format_reward(text: str) -> float:
    return 1.0 if re.search(r"<answer>.*?</answer>", text, re.S) else 0.0
```

# 17. GRPO 显存策略

**第一轮：**

```
num_generations = 2
max_completion_length = 256
batch_size = 1
gradient checkpointing = true
```

**如果显存不足：**

```
1. 减 num_generations
2. 减 max_completion_length
3. 减 image tokens
4. 减 max_length
5. 暂时关闭 vLLM rollout
6. 再考虑 QLoRA
```

# 18. GRPO 与 vLLM 的一个当前注意点

**当前工程主线建议：**

```
Image GRPO:
可以继续研究 vLLM rollout

Video GRPO:
暂时不要作为第一版主线
```

**原因：**

**Qwen3-VL 当前 image rollout 路径相对成熟，而 video rollout 在训练端和 vLLM 端的 multimodal prompt 对齐上仍可能遇到版本相关问题。**

**因此：**

```
SFT:
Text + Image + Video

GRPO:
Image only

最终推理:
Text + Image + Video
```

**这个方案最稳。**

        proxy_pass http://127.0.0.1:9000;
